**الحالة:** مرجع موحد للمراجعة والتنفيذ؛ لا يعني أن كل ما فيه منفذ أو مختبر.

> هذه الوثيقة هي نقطة البدء لأي نموذج ذكاء اصطناعي أو مطور يعمل على MSHKUR. اقرأها أولاً، ثم افحص الكود والاختبارات والحالة الحية قبل أي تغيير. عند التعارض، كود main العامل هو مصدر الحقيقة للتنفيذ، وقرارات المالك الصريحة الأحدث هي مصدر الحقيقة لنطاق المنتج.

## 0. تعليمات إلزامية لأي نموذج
1. لا تبدأ من الصفر. افحص المستودع والفرع وGit diff والوثائق والاختبارات والمهارات المسجلة.
2. لا تعتبر وجود شاشة أو ملف مهارة أو زر دليلاً على أن الوظيفة متصلة أو ناجحة.
3. صنّف كل معلومة: **قرار مالك معتمد / موجود في الكود / مقترح / غير موصول / غير مختبر / مؤجل / مرفوض**.
4. لا تعدل main مباشرة. أنشئ فرع عمل من أحدث main، ثم PR واضح، ولا تدمج دون موافقة المالك واجتياز بوابات الجودة.
5. ابحث أولاً عن مشروع مفتوح المصدر مناسب، وافهم بنيته وسلوكه وترخيصه، ثم قرر: إعادة استخدام مكتبة، adapter، fork مضبوط، أو تنفيذ مستقل. لا تستورد تطبيقاً كاملاً لمجرد أنه مشهور.
6. لا تشغل كوداً أو Skill أو MCP server أو workflow غير موثوق في بيئة الإنتاج. راجع المصدر، وثبّت الإصدار، واعزل التنفيذ، وقيّد الصلاحيات.
7. لا ترفع صورة المستخدم أو بياناته لمزود خارجي افتراضياً. المعالجة المحلية أولاً. أي نقل خارجي يتطلب سبباً واضحاً وموافقة.
8. لا تنفذ إرسالاً أو نشراً أو حذفاً أو تغييراً خارجياً دون موافقة صريحة على المحتوى والوجهة والفعل.
9. لا تخترع مواصفات سيارة أو سعرها أو حالتها أو عيوبها. النصوص تُبنى من الحقول الموثقة فقط.
10. لا تعلن نجاح اختبار أو اتصال أو نشر إلا بدليل تشغيل فعلي. اذكر الأمر والنتيجة والبيئة.
11. عند اكتشاف طريقة أفضل، قارنها بالحل الحالي في الجودة والسرعة والذاكرة والتكلفة والترخيص وسهولة الصيانة، ثم قدم توصية موثقة. لا تتقيد بقائمة المكتبات الحالية.
12. حافظ على التوافق مع تجربة عربية RTL وجوال أولاً، وابدأ من المهمة والنتيجة لا من لوحة تحكم مزدحمة.

## 1. تعريف مشكور والرؤية
MSHKUR منصة أدوات ومنتجات مصغرة لإنجاز الأعمال، تبدأ من نتيجة يريدها المستخدم. ليست لوحة تحكم تقليدية ولا سوقاً يعرض أسماء النماذج والمساعدين. المنتج الظاهر بسيط؛ أما المهارات والمساعدون والمحركات والموصلات والبحث والاختبار فتعمل خلف الكواليس.

**المبدأ:** ادخل، نفّذ المهمة، راجع النتيجة، ثم احفظ أو صدّر أو شارك.

### المنتجات الظاهرة المعتمدة في أحدث توجيه
1. **استوديو الصور / إزالة الخلفية**: دخول مباشر للأداة، رفع/تصوير، معالجة، مقارنة، تصحيح، تنزيل.
2. **استوديو الإعلان**: تحويل صور وبيانات السيارة الموثقة إلى حزمة إعلان قابلة للمراجعة والتصدير.
3. **المعرض والتاجر / مشكور سيارة**: ملف السيارة، المخزون، صفحة السيارة والمعرض، العملاء والمتابعة.
4. **«نسختك. سكرتيرك. صديقك»**: مساعد عام يعمل داخلياً مع التطبيقات والسياقات، وليس بالضرورة تطبيقاً مستقلاً أو واجهة مزدحمة.

**توضيح الهيكل:** في نقاشات سابقة ظهرت صيغ 3 منتجات، ثم 4 منتجات، كما ظهر متصفح ذكي للإدارة كتطبيق داخلي محتمل خامس. المرجع الأحدث يعتمد أربعة منتجات ظاهرة، ويعامل المتصفح الذكي كقدرة إدارية داخلية/تجريبية لا كمنتج عام حتى يصدر قرار جديد.

### مبادئ الدخول والتجربة
- فتح استوديو الصور مباشرة دون إجبار على التسجيل.
- الزائر يستطيع استخدام الأداة؛ التسجيل اختياري لحفظ الأعمال وربطها بمشروع سيارة.
- العودة للرئيسية متاحة ولا تحبس المستخدم داخل الأداة.
- العربية RTL أولاً، جوال أولاً، واجهة خفيفة ومختصرة.
- النتيجة والصورة هما مركز الشاشة؛ لا شروحات تسويقية طويلة ولا لوحة تحكم افتراضية.
- لا تظهر للمستخدم أسماء Skills أو Agents أو MCP أو مزودي النماذج إلا في أدوات الإدارة والتشخيص عند الحاجة.

## 2. قاعدة الأصل والنسخ — KeepOriginal
الأصل immutable وغير قابل للكتابة فوقه. كل تعديل ينتج ملفاً مشتقاً جديداً مرتبطاً بالأصل الجذري، مع recipe وإصدار وبصمة checksum.

### معنى الأوامر الوظيفية
- `removebackground/`: إزالة الخلفية من نسخة عمل وإنتاج نتيجة شفافة أو مشهد مختار.
- `keeporiginal/`: سياسة إلزامية لحماية الأصل، وعدم استبداله أو تعديله. لا تعني أن نموذج التوليد سيحافظ تلقائياً على كل تفاصيل النسخة المشتقة؛ لذلك نستخدم masks/reference constraints وQA ومقارنة.
- `restore/`: استعادة مناطق محددة من الصورة/القناع المرجعي.
- `erase/`: إزالة منطقة محددة من النسخة المشتقة فقط.
- `refineedges/`: تحسين الحواف وتقليل الهالات مع فحص التفاصيل.
- `blurplate/`: طمس لوحة السيارة؛ يدوي في المسار المثبت ما لم يجتز الكشف الآلي الاختبارات.
- `export/`: إخراج صيغة وأبعاد وجودة محددة.

هذه intents وليست shell commands. تُحوّل إلى Skills IDs مسجلة ومخططات مدخلات/مخرجات وصلاحيات معروفة. لا تنفذ نصاً حراً مولداً من النموذج.

### شروط القبول
- hash الأصل ثابت قبل وبعد كل معالجة.
- حفظ الأصل والنسخة المشتقة والقناع/الوصفة عند توفرها.
- مقارنة قبل/بعد وإصدارات متسلسلة.
- فحص حواف السيارة والزجاج والمرايا والعجلات والأسلاك والهوائيات والظلال.
- فشل واضح إذا تعذر ضمان سلامة الملف أو اكتمال الإخراج.

## 3. حرية النموذج في البحث والتحسين
للنموذج حرية واسعة في استكشاف GitHub والأبحاث والمكتبات والأدوات والطرق البديلة، بما فيها اكتشاف طريقة تختصر Skill أو تجمع عدة خطوات وتحقق جودة قريبة من أداة متخصصة كاملة، مثل بدائل Remove Background أو تحسينات KeepOriginal.

لكن الحرية ليست صلاحية دمج أو تشغيل غير محدود. اتبع دورة:
1. فهم الهدف ومقياس النجاح.
2. البحث عن المشاريع والأوراق والديموهات والتطبيقات المشابهة.
3. Reverse engineering قانوني قائم على السلوك المرئي والتوثيق، دون نسخ كود أو أصول محمية.
4. مقارنة عدة حلول، بما فيها حلول بسيطة غير معتمدة على نموذج كبير.
5. فحص الترخيص لكل من الكود والأوزان والبيانات والأصول والاعتماديات.
6. بناء تجربة صغيرة معزولة (POC) على بيانات اختبار مرخصة.
7. قياس الجودة والسرعة والذاكرة وحجم التنزيل وتكلفة التشغيل ودعم الأجهزة.
8. دمج الحل الأفضل خلف adapter وSkill contract، مع إبقاء fallback معروف.
9. إضافة اختبارات regression وgolden fixtures وسجل provenance.
10. تفعيل تدريجي بعد مراجعة المالك، دون تعديل main مباشرة.

**لا مساواة تلقائية بين الاختصار والجودة:** Skill قصيرة قد تعطي نتيجة ممتازة إذا استدعت محركاً جيداً أو سلسلة عمليات مضبوطة؛ لكنها لا تصبح مكافئة لأداة متخصصة إلا بعد benchmark يثبت ذلك. لا ادعاء «جودة مساوية» دون مجموعة اختبار ومعايير قبول.

## 4. البنية الهندسية المقترحة
### الطبقات
- **Product UI:** التطبيقات الأربعة الظاهرة، واجهات task-first.
- **Project Context:** هوية السيارة/الملف، الأصول، البيانات، النتائج، المسودات، الموافقات.
- **Maestro:** فهم intent، تخطيط DAG، اختيار Skills، ترتيبها، حالات التنفيذ، retry/cancel، approvals، events.
- **Skill Registry:** سجل موحد typed allowlist.
- **Tool adapters:** browser-local، server-local، model inference، connectors.
- **Agents/Assistants:** أدوار متخصصة في البحث والتصميم والهندسة والاختبار والأمن والترخيص؛ قد تكون أدواراً أو workflows ولا يشترط أن تكون نماذج مستقلة دائمة.
- **Asset & Data layer:** SQLite حالياً، تخزين ملفات دائم، صلاحيات tenant، نسخ احتياطي.
- **Policy & QA:** الأمان، الترخيص، الجودة، الخصوصية، بوابات التصدير والنشر.

### Maestro
Maestro منسق المهام، لا منفذ أوامر حرة. يحول طلب المستخدم إلى خطة من Skills معروفة، يتحقق من المدخلات والصلاحيات، يطلب الموافقة عند الحاجة، ثم ينفذ ويسجل النتيجة. يجب أن يظل engine الحالي هو الأساس ما دام كافياً؛ LangGraph وCrewAI مراجع مقارنة وليسا سبباً لإعادة كتابة النظام.

### Skill manifest المقترح
`id, version, description, inputSchema, outputSchema, runtime, handler, dependencies, model, weights, license, permissions, cost, timeout, memoryBudget, cancellation, idempotency, tests, provenance, failurePolicy`.

كل Skill لها:
- مدخلات ومخرجات typed.
- handler مسجل صراحة.
- صلاحيات أقل ما يمكن.
- مصدر وإصدار وترخيص.
- اختبار جودة وأمان.
- timeout وmemory budget وسياسة retry/cancel.
- سجل تنفيذ قابل للتدقيق.

### المساعدون / فريق المهارات
الأدوار الافتراضية حسب الحاجة:
Product & UX Research، Reverse Engineering، Architecture، React/Mobile/RTL، Backend/Data، Image ML، Skills/Maestro، Google Integrations، WhatsApp Compliance، QA/Accessibility/Performance، License/Supply Chain، Release/Hosting.
ليس مطلوباً أن تعمل كلها كنماذج منفصلة. يجب أن تعمل كمهارات قابلة للاستدعاء والتوثيق، ولا يدعي النظام فريقاً متصلاً ما لم تكن الأدوات مهيأة ومختبرة.

## 5. محرك الصور
### مراحل خط المعالجة
Intake/validation → EXIF normalize → حفظ original + checksum → plate privacy (عند طلبها) → segmentation → matte refinement → lighting/color → glass mask/tint → scene/background → shadow → QA → export.
الترتيب قابل للتكييف حسب intent، ولا يطبق أي تغيير على الأصل.

### محركات/مهارات
- MSH-SEG: فصل السيارة عن الخلفية.
- MSH-MATTE: تحسين alpha والحواف والثقوب والهالات.
- MSH-PLATE: اقتراح/تحديد اللوحة وطمسها مع تحقق التغطية.
- MSH-LIGHT: إضاءة وتباين وإضاءات وظلال.
- MSH-COLOR: توازن أبيض وحرارة وتشبع.
- MSH-GLASS: قناع زجاج وتظليل مع الحفاظ على الانعكاسات.
- MSH-SHADOW: الاحتفاظ بظل التلامس أو تركيبه.
- MSH-SCENE: خلفيات ومقاس وموقع ومنظور.
- MSH-QUALITY: فحص الحواف واللوحة والقص والملف.
- MSH-OUTPUT: PNG/JPEG/WebP وأبعاد وmetadata.

### درجات الحقيقة الحالية (حسب تدقيق main والوثائق)
- BG0/BiRefNet: موجود في main كإزالة خلفية محلية؛ الجودة على جميع صور السيارات والأجهزة لم تثبت بbenchmark شامل.
- طمس اللوحة: يدوي/محدد من المستخدم في المسار المثبت؛ الكشف الآلي ليس معتمداً.
- الزجاج: توجد تجربة/مكوّن تظليل يدوي في بعض الفروع/المواصفات؛ لا تفترض أنه موصول في main.
- إضاءة Canvas: تحسينات بسيطة وليست ترميماً توليدياً.
- خلفية الاستوديو والظل: تركيب Canvas تركيبي؛ ليس محاكاة فيزيائية أو توليداً واقعياً مضموناً.
- الإعلان: نص deterministic من حقول السيارة؛ لا LLM موصول افتراضياً.
- الصور: مسارات متعددة موجودة، لكن مشروع سيارة واحد يربط كل التدفقات يحتاج استكمالاً.
- KeepOriginal: قاعدة معمارية إلزامية؛ تحقق hash والربط بين الأصل والمشتقات في الاختبارات.

## 6. المنتجات ومسارات المستخدم
### Studio
فتح مباشر → التقاط/رفع → معالجة محلية → مقارنة → تصحيح القناع/الحواف → أدوات إضافية → حفظ مشتق/تنزيل/مشاركة.
لا تسجيل إجباري. لا API مدفوع إجباري.

### Ad Studio
اختيار مشروع السيارة → الصور المعالجة → إدخال/مراجعة الحقول → التحقق من النواقص → صياغة مسودة من الحقائق فقط → معاينة القوالب → تصدير.
النشر خطوة مستقلة وبموافقة.

### Dealer / Showroom
مخزون سيارات، ملفات سيارة، ألبومات، صفحة عامة، معلومات تواصل، استفسارات ومتابعة ومهام ومواعيد. ليس نظام CRM/DMS كاملاً في الإصدار الأول.

### General Assistant
واجهة مساعدة سياقية عند الحاجة داخل التطبيقات: فهم طلب، اقتراح خطة، استدعاء مهارات مسموحة، شرح مختصر للنتيجة، طلب الموافقة. ذاكرة محددة النطاق مع مصادر واضحة، ولا تنفيذ خارجي بلا إذن.

### المتصفح الذكي للإدارة
قدرة إدارية داخلية محتملة للبحث والتنقل وGitHub وHostinger والاختبار والنشر. يجب أن تعمل ضمن allowlist ومجالات محددة، وتعرض خطة وتطلب موافقة قبل النشر أو التغيير. ليست منتجاً عاماً مؤكداً.

## 7. التكاملات والقيود
- WhatsApp حالياً: روابط wa.me / مشاركة يدوية؛ لا WhatsApp Business API مدفوع، ولا أتمتة غير رسمية أو scraping أو إرسال تلقائي.
- WhatsApp channel: فتح الرابط/القناة ومشاركة يدوية بموافقة المستخدم؛ لا ادعاء بربط جلسة أو مزامنة.
- Google: روابط خرائط/deep links في المسار الحالي؛ Google OAuth/Drive/Calendar/Tasks/Docs/Sheets/Slides/Contacts تحتاج موصلات scopes واختبارات مستقلة.
- MCP: خادم محلي محدود؛ لا يضاف server أو tool لمجرد أن النموذج اقترحه. تسجيل وثقة وصلاحيات أولاً.
- APIs مدفوعة: لا تكون شرطاً للمسار الأساسي؛ أي مزود خارجي اختياري وواضح التكلفة.
- لا أسرار في الواجهة أو Git أو VITE env vars.
