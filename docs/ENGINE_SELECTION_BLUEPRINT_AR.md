# خريطة المحركات الهجينة — MSHKUR

> قرار هندسي وتجاري أولي — 17 نوفمبر 2026. هذا المستند يميز بين ما يعمل الآن، وما ندرسه، وما لا نعتمده قبل مراجعة المصدر والترخيص والاختبار.

## 1) الهدف التجاري

نبني منتجاً عربياً يخدم المعارض وتجار السيارات من المهمة إلى النتيجة: صورة جاهزة، إعلان صحيح، سيارة منشورة، استفسار مسجل، وعميل تتم متابعته. الربح يأتي من توفير الوقت ورفع جودة الإعلان وتحويل عمليات المعرض إلى تدفق واضح، لا من بيع الوصول إلى نموذج لغوي عام.

**القاعدة:** لا نبني منصة وكلاء عامة. نبني حزمة وظائف سيارات متخصصة، وكل وظيفة لها مدخلات واضحة ومخرجات قابلة للمعاينة والتصحيح.

## 2) البنية المستهدفة بأقل تشغيل

| الطبقة | قرار MSHKUR | لماذا |
|---|---|---|
| واجهة المهام | React + TypeScript + PWA | موجودة؛ تطبيق ويب واحد يعمل على الهاتف والكمبيوتر |
| API والمحرك | Node.js + Express داخل عملية واحدة أولاً | لا خادم مستقل لكل محرك |
| البيانات | SQLite WAL على قرص دائم | أقل كلفة وتعقيد لنسخة معرض/خادم واحد |
| الصور | معالجة المتصفح أولاً، وSharp محلياً للعمليات الخادمية | لا رفع غير لازم ولا GPU server |
| المهارات | handlers موثوقة داخل allowlist + manifests | لا تشغيل كود مستورد عشوائياً |
| سير العمل | محرك MSHKUR صغير قابل للاستئناف فوق SQLite | يكفي للخطوات القصيرة دون Temporal/Redis/Postgres الآن |
| الذكاء | قواعد دقيقة أولاً؛ نموذج محلي اختياري لاحقاً | لا API مدفوع شرطاً للمنتج |
| الموصلات | وحدات اختيارية بموافقة المستخدم | لا Google ولا WhatsApp ولا خدمات خارجية شرطاً |

لا نضيف Redis أو Kubernetes أو PostgreSQL أو عمالاً منفصلين قبل وجود قياس يثبت أن الحمل يحتاجها. SQLite لا يناسب عدة خوادم تكتب بكثافة؛ عند الوصول لهذه العتبة نخطط للترحيل بدلاً من دفع ثمن التعقيد مبكراً.

## 3) محركات الوظائف المقترحة

### A. محرك صور السيارات

**المسار:** اختيار الصور ← إزالة الخلفية ← تحسين الحواف ← طمس اللوحة ← إعداد الزجاج/الظل/الخلفية ← قصّ ومقاسات المنصات ← ضغط WebP/JPEG ← معاينة ← تنزيل/ربط بسجل السيارة.

- الموجود حالياً: إزالة خلفية محلية عبر BG0/BiRefNet، طمس مستطيل يدوي، تحسين WebP عبر Sharp، ومعالجة دفعات متسلسلة.
- التالي: لوحة أدوات موحدة على الصورة نفسها؛ undo/redo؛ مقارنة قبل/بعد؛ إلغاء وإعادة محاولة كل صورة؛ حفظ preset للمعرض؛ معالجة مجموعة صور مع سجل واضح.
- لا نزعم كشف لوحة تلقائياً أو تظليل زجاج واقعي حتى تنفذ وتختبر.
- لا نرفع الصورة إلى أي خدمة خارجية في المسار الافتراضي.

**مصدر مرجعي:** BG0 يوفر إزالة خلفية محلية في المتصفح، مع WebGPU وWASM وبدون API أو خادم inference. كود BG0 مرخص Apache-2.0، لكن أوزان النماذج وإشعارات الأطراف الثالثة لها تراخيص مستقلة؛ يجب فحصها لكل revision قبل التوزيع التجاري.  
https://github.com/opencoredev/bg0  
https://bg0.dev/docs

**مرشح لا نعتمده تلقائياً:** rembg مشروع MIT، لكن أوزان النماذج منفصلة؛ المصدر يذكر أن نموذج BRIA الافتراضي يحتاج اتفاقاً تجارياً مدفوعاً. لذلك لا نخلط ترخيص المكتبة بترخيص النموذج.  
https://github.com/danielgatis/rembg

### B. محرك سير العمل Maestro

بدلاً من إدخال Temporal أو Conductor أو Airflow الآن، نكمل المحرك الموجود:

- تعريف workflow بإصدار ثابت ومخطط مدخلات/مخرجات.
- خطوة واحدة = skill موثوقة ذات صلاحيات معلنة.
- حفظ حالة كل خطوة ونتيجتها ووقت التنفيذ.
- idempotency key لمنع تكرار نفس العملية.
- retry محدود للأخطاء المؤقتة فقط.
- إلغاء آمن للمهام التي لم تبدأ؛ لا نقطع كتابة ملف في منتصفها.
- checkpoint/resume بعد إعادة تشغيل Node.
- قياس مدة كل خطوة وحجم المدخلات والمخرجات.
- سجل أخطاء مفهوم للمستخدم مع تفاصيل تقنية في الإدارة.

**قرار البنية:** نبقى على SQLite ومحركنا الداخلي للمرحلة الأولى. ندرس OpenWorkflow كمرجع TypeScript/SQLite/Apache-2.0. هندسته تعتمد قاعدة بيانات كحقيقة وحيدة، مع workers stateless تسحب المهام وتستخدم leases/heartbeats وstep attempts للاستئناف بعد التعطل؛ لا يوجد orchestrator server منفصل، لكن التشغيل يتطلب worker process داخل بنيتنا. هذا مرجع مفيد لتصميم الاستئناف والـ leases، وليس سبباً لإضافة اعتماد الآن. المشروع ما زال 0.x وفق آخر مراجعة؛ لا نعتمده قبل فحص API واختبار workflow فعلي.  
https://github.com/openworkflowdev/openworkflow

Temporal وHatchet وTrigger.dev وConductor خيارات قوية عندما نحتاج عمالاً متعددين وتنسيقاً موزعاً، لكنها تضيف خدمات وقواعد بيانات/طوابير أو تشغيلاً منفصلاً؛ ليست حاجة حالية.

### C. محرك الإعلان والمخزون

- مصدر الحقيقة هو سجل السيارة وحقول المستخدم، لا تخمين النموذج.
- توليد عنوان ووصف ومواصفات من الحقول المؤكدة فقط.
- قوالب حسب نوع السيارة والمنصة واللغة.
- كشف الحقول الناقصة والتعارضات قبل إنشاء الإعلان.
- إنشاء نسخ متعددة للنبرة/الطول مع عدم اختلاق مواصفات.
- حفظ draft/version وتاريخ التعديل.
- النشر يبقى خطوة منفصلة بموافقة المالك.

### D. محرك العملاء والاستفسارات

- inbox موحد لاستفسارات الموقع وروابط التواصل التي يختارها المستخدم.
- تحويل الاستفسار إلى lead مربوط بسيارة/مصدر/وقت.
- حالات متابعة بسيطة: جديد، تم التواصل، موعد، تفاوض، مغلق.
- مهام تذكير وملاحظات ومالك متابعة.
- لا scraping لأرقام أشخاص ولا إرسال جماعي آلي ولا WhatsApp API قبل موافقة وإعداد رسمي.

### E. محرك صفحات المعرض

- صفحة عامة سريعة لكل معرض مع سيارات منشورة فقط.
- صفحة سيارة قابلة للمشاركة وQR.
- بيانات SEO أساسية وصور محسنة.
- نموذج استفسار واضح مع موافقة على حفظ البيانات.
- لا نعتمد بوابة دفع أو استضافة صور خارجية في أول إصدار.

### F. محرك المعرفة والمساعد

- FAQ وقواعد محلية أولاً.
- استرجاع من بيانات المعرض والمهارات المسموح بها.
- LLM محلي اختياري خلف adapter متوافق؛ لا fallback سحابي صامت.
- أي إجابة تتعلق بسعر/عداد/مواصفة يجب أن تشير إلى حقل مصدرها.
- الوكيل لا يرسل أو ينشر أو يشتري أو يحذف نيابة عن المستخدم دون موافقة.

## 4) REA: طريقة البحث وإعادة البناء

REA المقصود هو Reverse Engineer Anything من morluto/rea، أداة تطوير عبر MCP وليست محرك إنتاج لمستخدمي MSHKUR.

لكل مشروع ندرسه، ننشئ بطاقة أدلة:

1. رابط المصدر والمالك وتاريخ آخر تحديث.
2. LICENSE الفعلي وSPDX وملفات NOTICE.
3. تراخيص منفصلة للنماذج والأوزان والخطوط والأيقونات والبيانات.
4. نقطة الدخول ورحلة المستخدم.
5. المدخلات، المخرجات، الصيغ، الدقة، حدود الحجم.
6. مراحل المعالجة والخوارزميات والاعتماديات.
7. حالات الخطأ والتراجع والإلغاء.
8. ما يعمل offline وما يحتاج شبكة/حساباً/خادماً.
9. تكلفة الموارد على CPU/RAM/GPU وحجم التنزيل.
10. قرار: adopt / adapt / reimplement / reject مع السبب.

نستخدم REA على البرامج والمستودعات التي نملك حق فحصها أو المفتوحة وفق شروطها. لا نتجاوز تسجيل الدخول أو CAPTCHA أو حماية تقنية، ولا نستخرج أسراراً أو شيفرات خاصة. نستفيد من السلوك العام ونكتب تنفيذنا المستقل، إلا إذا كان الترخيص يسمح بدمج الكود ونستوفي التزاماته.

المصدر: https://github.com/morluto/rea — MIT وفق بيانات المستودع، ويجب إعادة التحقق من النسخة قبل تثبيت أداة التطوير.

## 7) كيف نربح دون أن نتحول إلى خدمة مكلفة

نموذج تجاري مقترح للاختبار، وليس تسعيراً نهائياً:

- **فردي:** عدد محدود من عمليات تجهيز الصور والإعلانات، وإدارة سيارات بسيطة.
- **معرض:** اشتراك شهري لكل معرض يشمل المخزون وصفحة المعرض والعملاء وسير العمل.
- **باقة نمو:** قوالب إضافية، تقارير، فريق ومهام متابعة، وقياس أداء الإعلانات.
- **رصيد معالجة اختياري:** فقط للوظائف التي تستهلك موارد أعلى بعد قياسها؛ لا نبيع رصيداً لميزة محلية مجانية بلا تكلفة متغيرة.
- **خدمات إعداد مدفوعة:** استيراد مخزون المعرض، تجهيز الهوية والقوالب، وترحيل البيانات.
- **خطة خاصة لاحقاً:** تثبيت محلي/خاص للمعارض الكبيرة إذا أثبت الطلب ذلك.

لا نعتمد الربحية على تشغيل GPU server أو استدعاءات LLM لكل نقرة. نقيس تكلفة الصورة والعميل النشط والاحتفاظ والتحويل قبل تحديد السعر.

## 8) ترتيب التنفيذ

### P0 — إكمال ما لدينا
1. إكمال أداة صور واحدة من رفع الصورة إلى ملف إعلان جاهز.
2. تحسين محرك الدفعات: إلغاء، retry، تقدم، سجل لكل صورة.
3. تقوية Workflow engine: validation للمخطط، idempotency، retry، resume، logs.
4. إضافة اختبارات حقيقية لصور السيارات وtenant isolation.

### P1 — قيمة تجارية مباشرة
5. صفحة سيارة ومعرض عامة مع QR.
6. Inbox وLead pipeline وربط الاستفسار بالسيارة.
7. قوالب إعلان متعددة مع مصدر كل معلومة.
8. تقارير بسيطة: زمن التجهيز، عدد الإعلانات، الاستفسارات.

### P2 — البحث والاستيراد
9. استيراد المستودعات إلى quarantine دون تشغيلها.
10. تقرير آلي للترخيص والاعتماديات وملفات النماذج.
11. REA evidence cards للرحلات والمخرجات.
12. تحويل الوظائف المنتقاة إلى handlers مستقلة داخل MSHKUR.

### P3 — بعد إثبات الحاجة
13. نموذج محلي اختياري بمقارنة سرعة/ذاكرة/جودة عربية.
14. موصلات خارجية رسمية بموافقة واضحة.
15. نقل قاعدة البيانات أو فصل العمال فقط عندما تتطلبه مؤشرات الحمل.

## 9) بوابات قبول كل محرك

لا نقول إن المحرك جاهز حتى تتوفر:
- مدخلات ومخرجات موثقة.
- عينة اختبار ثابتة ونتيجة قابلة لإعادة الإنتاج.
- اختبار نجاح وفشل وإلغاء.
- فحص خصوصية وعدم تسريب الصور/بيانات المعرض.
- ترخيص واضح لكل ملف موزع.
- اختبار على هاتف متوسط وجهاز كمبيوتر.
- زمن تنفيذ وحجم تنزيل معروفان.
- شرح واضح لما يحدث محلياً وما يرسل خارج الجهاز.

**الحالة:** هذه خريطة قرار وبحث وليست ادعاء بأن كل المحركات أعلاه نُفذت. التنفيذ الحالي يبقى هو ما يثبته الكود والاختبارات فقط.
