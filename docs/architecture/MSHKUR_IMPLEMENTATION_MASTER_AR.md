## 1. الغرض ومصدر الحقيقة

هذه الوثيقة تجمع رؤية المنتج، تصميم تجربة المستخدم، التطبيقات، المحركات، البيانات، الصلاحيات، التكاملات، الاختبارات، ومراحل التنفيذ. وهي مكتوبة لتكون قابلة للتسليم إلى مطور أو نموذج ذكاء اصطناعي آخر دون الاعتماد على المحادثات السابقة.

ترتيب مصادر الحقيقة:
1. الكود الحالي والاختبارات وسجلات CI والنشر.
2. تعليمات المستودع وملفات `AI_CONTEXT.md` و`AI_HANDOFF.md` و`AI_CHANGELOG.md`.
3. هذه الوثيقة والوثائق التخصصية.
4. المحادثات والملاحظات بوصفها سياقاً مساعداً فقط.

يجب أن يبدأ أي وكيل من قراءة `AGENTS.md` إن وجد، ثم تعليمات المشروع وملفات السياق والتسليم والتغيير، وبعدها يفحص الشيفرة والفروع والاختبارات قبل تعديل أي شيء.

### قواعد لا تقبل الاستثناء
- تطوير المستودع الحالي؛ لا إنشاء مشروع بديل ولا هدم العمل الموجود.
- المحافظة على التصميم المرجعي ومبادئه، وعدم استبداله بقالب SaaS عام.
- لا تُعرض وظيفة أو إضافة كأنها تعمل قبل ربطها واختبارها فعلياً.
- لا تُعرض نتائج صور أو أصوات أو فيديوهات تجميلية على أنها نتائج محرك حقيقي.
- الحفاظ على الملف الأصلي وإنشاء نسخة مشتقة مستقلة قابلة للتتبع.
- لا إرسال أو نشر أو حذف أو مشاركة خارجية حساسة دون موافقة مناسبة.
- لا وضع أسرار أو مفاتيح API في الواجهة.
- توثيق ما تم اختباره وما لم يتم اختباره بدقة.

## 2. تعريف المنتج

MSHKUR منظومة تطبيقات ذكية متخصصة تعمل فوق طبقة تنفيذ مشتركة. ليست لوحة تحكم تقليدية، وليست مجرد نافذة دردشة.

المبدأ المركزي لتجربة الاستخدام:

**Tool → Input → Execute → Result**

1. يعرف المستخدم المهمة من اسم واضح أو زر أو صوت.
2. يطلب النظام أقل قدر لازم من البيانات.
3. يعرض ما سيحدث ويبدأ التنفيذ بعد التأكيد عند الحاجة.
4. يعرض التقدم والنتيجة والخطوة التالية بوضوح.

يجب أن تخدم الواجهة أشخاصاً لا يجيدون كتابة الأوامر أو لا يفضلونها. لذلك يجب توفير الصوت والأزرار والإجراءات الجاهزة جنباً إلى جنب مع الكتابة.

### المنتجات المستقلة
1. **MSHKUR iAI:** مساعد شخصي مستقل داخل مشكور.
2. **Photo Studio:** استوديو مستقل لمعالجة صور السيارات.
3. **Ad Studio:** استوديو مستقل لإنشاء محتوى وإعلانات السيارات.
4. **Dealer Workspace:** تطبيق مستقل لتسجيل المعارض وإدارة بياناتها ومخزونها.
5. **Admin Browser / Workbench:** مساحة إدارة وتشغيل وصيانة للمالك، تؤجل إلى مرحلة لاحقة.

تستطيع iAI استدعاء وظائف المنتجات عند الحاجة، لكن هذا لا يلغي استقلال التطبيقات أو مساراتها أو صلاحياتها.

## 4. تجربة MSHKUR iAI

### 4.1 الشخصية
- شخصية صغيرة متناسقة مع مساحة الشاشة ولا تزاحم المهمة.
- تخصيص الاسم والمظهر والثيم.
- مسار مستقبلي لإنشاء شخصية وخلفية وصور، وإضافة أبعاد 3D عند ثبوت الحاجة.
- لا تجعل الشخصية رسماً ضخماً أو شاشة افتتاحية تعيق الوصول إلى العمل.
- أي إنشاء صور أو 3D يجب أن يستخدم محركاً حقيقياً موصولاً؛ وإلا يعرض كخيار غير متاح أو نموذج معاينة واضح.

### 4.2 الصفحة الرئيسية
تتضمن:
- ترحيباً موجزاً وسياقاً مناسباً.
- شخصية صغيرة.
- حقل كتابة اختياري.
- ميكروفون بارز وسهل اللمس.
- أزرار مهام جاهزة مثل: ابحث، نظّم، أنشئ، لخّص، جهّز إعلاناً، افتح أعمالي.
- وصولاً واضحاً إلى المهام والمكتبة.
- إجراءات سياقية عند وجود ملف أو سيارة أو مشروع محدد.

لا تضع كل القدرات في الصفحة الرئيسية. اعرض الإجراء الأكثر صلة بالسياق، واجعل بقية الوظائف في المكتبة أو داخل المنتج المختص.

### 4.3 الصوت وإمكانية الاستخدام
- إدخال صوتي واضح مع حالات: جاهز، يستمع، يحوّل الكلام إلى نص، يحتاج تأكيداً، فشل.
- إظهار النص المحول قبل تنفيذ الطلبات الحساسة أو الملتبسة.
- السماح بتعديل النص أو إلغائه.
- زر إيقاف واضح أثناء الاستماع والمعالجة.
- لا تشغّل الصوت تلقائياً.
- لا تجعل الكتابة شرطاً لاستخدام التطبيق.
- أزرار كبيرة ذات أسماء مفهومة وأهداف لمس مناسبة.
- تعليمات قصيرة بلغة المستخدم، وتجنب المصطلحات التقنية.
- دعم لوحة المفاتيح وقارئ الشاشة والتباين وتكبير النص.

### 4.4 شبكة الوكلاء
تعمل شبكة الوكلاء خلف الواجهة:
- البحث.
- التفاوض وصياغة المقترحات.
- التنسيق.
- المواعيد.
- تحليل المعلومات.
- إنجاز خطوات المهام المتخصصة.

يعرض iAI ملخصاً مفهوماً: من يعمل على ماذا، وما الذي اكتمل، وما الذي يحتاج موافقة. لا يعرض شبكة تقنية مزدحمة أو أسماء وكلاء داخلية للمستخدم العادي.

لا يتواصل وكيل مع طرف خارجي أو يرسل أو يحجز أو يشتري أو ينشر دون صلاحية وموافقة المالك المناسبة.

## 5. المهام والمكتبة والتخصيص

### 5.1 Tasks Workspace
كل مهمة لها:
- اسم واضح وسبب الإنشاء.
- حالة حقيقية.
- مراحل متتابعة.
- نتيجة أو مخرجات.
- سجل أحداث.
- إيقاف واستئناف حيث يسمح المحرك.
- تأجيل.
- إلغاء.
- إعادة محاولة آمنة.
- طلب موافقة.
- عرض ما نجح وما فشل في النتائج الجزئية.

حالات موحدة:
`CREATED`, `VALIDATING`, `QUEUED`, `RUNNING`, `WAITING_APPROVAL`, `SUCCEEDED`, `PARTIAL`, `FAILED`, `CANCELLED`, `TIMED_OUT`.

لا تعرض المهمة على أنها قيد التنفيذ ما لم تبدأ فعلياً. يجب أن تتطابق مؤشرات الواجهة مع حالة Task Engine.

### 5.2 Library
المكتبة مساحة منظمة تشمل:
- التطبيقات والاستوديوهات.
- المهارات المتاحة.
- المشاريع.
- المخرجات والملفات.
- الأعمال الأخيرة.
- المصادر والمراجع التي يملك المستخدم صلاحية الوصول إليها.

ليست المكتبة قائمة جهات اتصال، ولا مكاناً لعرض تكاملات غير موصولة كأنها نشطة.

أيقونات الخدمات الخارجية:
- استخدم أيقونات/شعارات أصلية أو مرخصة حيث تتوفر.
- لا تكتب اسم الموقع بجانب كل أيقونة إذا كانت الأيقونة معروفة؛ وفر اسماً بديلاً لقارئ الشاشة وTooltip عند الحاجة.
- لا تستخدم الشعار للإيحاء بأن الاتصال قائم.

### 5.3 Profile & Themes
- اسم الشخصية.
- صورة أو Avatar.
- ثيم فاتح افتراضي.
- ثيم داكن وثيمات لونية إضافية.
- خلفية قابلة للتخصيص.
- إعدادات اللغة والاتجاه.
- إعدادات الصوت والخصوصية.
- إظهار ما إذا كان التخصيص محلياً على الجهاز أو متزامناً عبر حساب.

لا توحِ بمزامنة سحابية إذا كان الحفظ محلياً فقط.

## 6. المنتجات المتخصصة

### 6.1 Photo Studio
تطبيق مستقل لإزالة خلفية السيارة وتجهيز صورها:
- اختيار صورة من الملفات أو الكاميرا.
- معاينة الأصل.
- تنفيذ المعالجة.
- مراجعة الحواف.
- اختيار خلفية بيضاء أو شفافة.
- مقارنة قبل/بعد.
- اعتماد النتيجة.
- تنزيل النسخة المشتقة.
- حفظ سجل العمل.

**قاعدة قبل/بعد:** يجب أن تكون الصورتان لنفس السيارة ومن نفس الملف الأصلي/معرف الأصل، مع نفس زاوية التصوير. لا تستخدم صورتين لسيارتين مختلفتين لإيهام المستخدم بأنهما قبل/بعد. تحفظ العلاقة عبر `source_asset_id` و`derived_asset_id`، ويكون شريط المقارنة فوق الأصل والنتيجة الفعلية.

- الأصل لا يُستبدل.
- لا تُعرض عينة زخرفية على أنها ناتج محرك.
- الصور التجريبية يجب أن تكون مرخصة وموسومة بأنها أمثلة.
- اعرض حالة المحرك بصدق.
- استخدم نتائج فعلية محفوظة من نفس صورة الإدخال.
- يدعم الهاتف والكمبيوتر والسحب باللمس والماوس وبديل لوحة المفاتيح.

المعالجة الحالية في المستودع تستخدم `@bg0/browser` كاعتماد طرف ثالث. لا تصفها بأنها نموذج داخلي مدرّب.

### 6.2 Ad Studio
- توليد مسودة إعلان من حقول سيارة موثقة.
- عنوان ووصف قصير وطويل.
- تهيئة النص لقنوات مختلفة.
- إرفاق صور أصلية أو مشتقة مع بيان حالتها.
- مراجعة وتحرير واعتماد.
- تصدير أو نشر فقط عبر تكامل حقيقي وموافقة.

لا يخترع النظام السعر أو الممشى أو المواصفات. البيانات المفقودة تبقى غير محددة.

### 6.3 Dealer Workspace
تطبيق مستقل عن Photo Studio، مع تكامل سياقي بينهما.

#### تسجيل المعرض
- اسم المعرض والاسم التجاري.
- اسم المسؤول.
- رقم الهاتف والبريد.
- المدينة والعنوان.
- وصف النشاط.
- الشعار وصورة الغلاف.
- روابط التواصل والموقع.
- الموافقة على الشروط والخصوصية.
- حالة التحقق.

#### لوحة المعرض
- نظرة عامة.
- ملف المعرض.
- السيارات والمخزون.
- إضافة/تعديل سيارة.
- صور السيارة.
- الإعلانات.
- طلبات العملاء.
- المحادثات.
- المواعيد وتجارب القيادة.
- تقارير.
- إعدادات الموظفين والصلاحيات.

#### بيانات السيارة
`id`, `organization_id`, make, model, year, trim, price, currency, mileage, fuel_type, transmission, color, condition, description, images, listing_status, created_at, updated_at.

الحالات: مسودة، قيد المراجعة، منشور، محجوز، مباع، مؤرشف.

#### الربط مع Photo Studio
يمكن فتح الاستوديو من سجل سيارة محدد وتمرير معرف السيارة والصور. يعيد الاستوديو نسخاً مشتقة مرتبطة بالسيارة. يبقى لكل تطبيق مساره وشاشته وصلاحياته.

## 7. Admin Browser / Workbench — المرحلة اللاحقة

هذه شاشة مستقلة للإدارة والمالك فقط، ولا تُدمج مع تجربة iAI للمستخدم النهائي.

أهدافها:
- إدارة التطبيقات والوحدات.
- إدارة المهارات وإصداراتها.
- إدارة الإضافات والتكاملات.
- إدارة المساعدين والوكلاء.
- بناء ومراجعة Workflows.
- مراجعة المهام والسجلات والأدلة.
- إدارة الموافقات والصلاحيات.
- فحص الصحة والأداء والتكلفة.
- البحث والتقييم.
- إدارة النسخ الاحتياطية والاستعادة.
- صيانة النظام والتحديث والتراجع.
- تعديل إعدادات العرض والمحتوى والخصائص المسموح بها.
- مراجعة وتعديل إعدادات المنتجات والواجهات من خلال صلاحيات واضحة وسجل تدقيق.

### صلاحيات الإدارة
- Owner: تحكم كامل مع حماية إضافية.
- Admin: إدارة تشغيلية محددة.
- Operator: تشغيل ومراقبة دون صلاحيات تغيير حساسة.
- Auditor: قراءة الأدلة والسجلات.
- لا تُعرض أدوات المالك أو مفاتيح الأسرار لمستخدم المعرض أو المستخدم العام.

كل تعديل إداري يسجل: الفاعل، الإجراء، القيمة السابقة/الجديدة عند ملاءمة ذلك، الوقت، السبب، نتيجة العملية، ومعرف الموافقة. التغييرات الحساسة تتطلب تأكيداً صريحاً وربما موافقة ثانية.

**التنفيذ مؤجل:** لا نبني Workbench الآن على حساب إكمال تجربة iAI والجوال والتطبيقات الأساسية. نضع عقوده وصلاحياته في المعمارية، ونبدأ واجهته بعد استقرار أساس المنتج.

## 8. المعمارية التقنية

### 8.1 الطبقات
1. Frontend Applications: iAI، Photo Studio، Ad Studio، Dealer Workspace، ثم Workbench.
2. Shared UI: Design System، Localization، Navigation، Upload، Task UI، Accessibility.
3. API Layer: Auth، Users، Organizations، Dealers، Vehicles، Media، Tasks، Skills، Workflows، Integrations.
4. Smart Layer: Task Engine، Planner، Skill Registry، Skill Runtime، Assistant Manager، Workflow Engine، Permissions، Approval Gate، Evidence، Audit، Recovery.
5. Execution Services: Image، Audio، Video، Content، Research، Connectors.
6. Infrastructure: Database، Object Storage، Queue، Cache، Logs، Metrics، Backups.
7. Delivery: CI، Unit/Contract/Integration/E2E/Visual/Security/Performance tests.

### 8.2 التقنيات الموجودة
المستودع الحالي يستخدم React وTypeScript وVite وNode.js/Express وSQLite وSharp وZod وPWA. لا تستبدل هذه البنية دون قياس ومبرر. GitHub Pages يعرض الواجهة الثابتة ولا يشغل Express أو SQLite أو عمال المعالجة الخلفية.

### 8.3 حدود التشغيل
- Browser: واجهة، معاينة، مهام محلية خفيفة عند ملاءمتها.
- Backend: حسابات وصلاحيات وبيانات وملفات وموافقات وواجهات API.
- Workers: المهام الثقيلة والطويلة والمعالجة بالدفعات.
- Storage: ملفات أصلية ومشتقة وصور مصغرة ومرفقات.
- Database: بيانات منظمة وعلاقات وسجلات.

اختيار مكان التنفيذ يعتمد على الخصوصية والأداء والتكلفة وموارد الجهاز، لا على الافتراض.

## 9. Shared Smart Layer

### 9.1 Task Engine
ينشئ المهمة، يتحقق من المدخلات والصلاحيات، يضعها في الطابور، يتابع الحالة، يدير الإلغاء وإعادة المحاولة، ويحفظ المخرجات والأحداث.

### 9.2 Skill Registry & Runtime
المهارة وحدة تنفيذ وليست Prompt أو زر واجهة. كل مهارة تتضمن:
- ID وإصدار ووصف وفئة.
- مدخلات ومخرجات typed.
- Runtime وHandler مسموح.
- صلاحيات.
- اعتماديات ومصدر وترخيص.
- حدود وقت وحجم وموارد.
- اختبارات.
- معالجة أخطاء.
- معايير جودة.
- حالة اعتماد.

دورة الحياة:
`DISCOVERED → REVIEW_REQUIRED → QUARANTINED → TESTING → APPROVED → ENABLED → MONITORING`، مع `DISABLED` و`ROLLED_BACK` عند الحاجة.

لا يُشغّل كود مستورد تلقائياً. لا شبكة افتراضياً للمهارات غير الموثوقة. لا تعرض مهارة كمتاحة إذا لم يوجد لها Handler حقيقي.

### 9.3 Assistant Manager
iAI هو المنسق العام. الأدوار المتخصصة تشمل الصور والإعلانات وتشغيل المعارض والبحث والهندسة، لكنها تعمل بحدود تفويض واضحة ولا تتجاوز صلاحيات المستخدم.

### 9.4 Workflow Engine
يربط عدة مهارات في سير عمل قابل للإصدار والاختبار والإيقاف والاستئناف والتراجع حيث يمكن. مثال تجهيز إعلان سيارة:
سجل السيارة → التحقق من البيانات → اختيار الصور → معالجة الصور → مراجعة الجودة → كتابة الإعلان → موافقة المالك → حفظ المسودة/التصدير.

### 9.5 Permissions & Approval Gate
كل إجراء خارجي أو حساس يتحقق من المستخدم والـ tenant والنطاق والمهارة والمورد. الموافقة محددة بالفعل والبيانات والجهة والمدة، وليست تفويضاً عاماً مفتوحاً.

### 9.6 Evidence, Audit & Recovery
يحفظ النظام الأدلة، وإصدار المهارة والمحرك، والمدخلات المرجعية، والمخرجات، ووقت التنفيذ، والفاعل، والأخطاء، وقرار الموافقة. يدعم الاستعادة وإعادة المحاولة الآمنة.

## 16. تجربة التصميم والاختبار

### التصميم
- فاتح افتراضياً، ثيم داكن وثيمات إضافية اختيارية.
- نظيف وهادئ، مع إبراز المهمة والصورة والنتيجة.
- لا تضع MSHKUR أو الشعار في الترويسة العلوية لواجهة الاستوديو؛ هذا قرار موثق من مراجعة المالك.
- لا تضع أسماء الخدمات بجانب الأيقونات المعروفة في المكتبة؛ استخدم Accessible Label وTooltip.
- لا تكثر البطاقات ولا تكرر الشروحات.
- لا تستخدم ألواناً أو شارات لزخرفة المعلومات.
- حافظ على اتساق الأيقونات والخط والمسافات والحواف.

### Mobile-first
اختبر 320، 360، 375، 390، 430px ثم Tablet وDesktop.
- لا تمرير أفقي ولا قص ولا تداخل.
- أهداف لمس مريحة.
- الإجراءات الأساسية واضحة.
- لا تصغّر تخطيط سطح المكتب فقط.
- راعِ Safe Areas.
- اختبر RTL وLTR وتكبير النص.

### Accessibility & Motion
- لوحة مفاتيح وتركيز مرئي.
- قارئ شاشة وتسميات بديلة.
- تباين مناسب.
- بديل لوحة مفاتيح لمقارنة الصور بالسحب.
- احترام `prefers-reduced-motion`.
- تحميل كسول للصور والفيديو.
- لا صوت تلقائي ولا فيديو ثقيل يحجب أول تفاعل.

### حالات كل شاشة
Empty، Loading، Processing، Success، Error، Offline، Not Connected، Needs Setup، Needs Approval، Cancelled، Partial Result.

### معايير قبول قبل/بعد
- الأصل والنتيجة لنفس السيارة ومن نفس المصدر.
- يحتفظ النظام بمرجع المصدر والنسخة المشتقة.
- يستطيع المستخدم مقارنة الاثنين بوضوح.
- النتيجة المعروضة هي نتيجة محرك فعلية.
- يمكن مراجعة الحواف واعتمادها قبل التصدير.
- لا تفقد الصورة الأصلية عند الفشل أو إعادة المحاولة.

## 17. مراحل التنفيذ وبوابات القبول

### Gate 0 — Baseline & Recovery
- مراجعة تعليمات المشروع والفروع وPRs وCI.
- إصلاح الموانع التي تمنع البناء.
- حصر الوظائف الموجودة والناقصة.
- تحديد خط أساس قابل للتكرار.

**القبول:** بناء واختبارات واضحة أو تسجيل سبب الفشل بدقة.

### Gate 1 — iAI Shell & UX
- دمج Organizing Companion وMinimal Chat-First وOrbit Workspace.
- الصفحة الرئيسية والشخصية والتخصيص.
- الكتابة والصوت والأزرار الجاهزة.
- تنقل واضح.
- RTL/LTR وجوال أولاً.

**القبول:** مسار استخدام مفهوم دون كتابة إلزامية، وأزرار موصولة بوظائف حقيقية أو معلمة بوضوح كغير متاحة.

### Gate 2 — Tasks & Library
- مراحل المهمة وحالاتها.
- الموافقات والإيقاف والتأجيل والإلغاء.
- مكتبة التطبيقات والمشاريع والمهارات والمخرجات.
- أيقونات أصلية مع أسماء بديلة للإتاحة.

**القبول:** كل حالة مستمدة من مصدر حقيقي، ولا توجد بطاقات اتصال وهمية.

### Gate 3 — Photo Studio Quality
- تحسين تخطيط الجوال وسطح المكتب.
- مقارنة قبل/بعد لنفس السيارة والمصدر.
- مجموعة صور مرخصة ومتنوعة.
- GIF/فيديو توضيحي خفيف عند توفر مادة حقيقية.
- قياس جودة القناع والأداء.

**القبول:** صورة أصلية ونتيجة فعلية مرتبطة بها، واختبار responsive وتفاعلي.

### Gate 4 — Dealer Workspace & Ad Studio
- تسجيل المعرض.
- الملف التجاري.
- المخزون والسيارات والصور.
- مسودات الإعلانات.
- ربط سياقي آمن بالاستوديو.

**القبول:** عزل بيانات المعارض واختبار مسارات CRUD والصلاحيات.

### Gate 5 — Smart Layer
- Skill Registry/Runtime.
- Task Engine.
- Assistant Manager.
- Workflow Engine.
- Permissions/Approval.
- Evidence/Audit/Recovery.

**القبول:** عقود واختبارات وتسجيل أدلة فعلية لكل مسار.

### Gate 6 — Integrations & Voice/Media
- تقييم وربط الصوت والتفريغ والفيديو والمعرفة والمشاريع والمحادثات والمواعيد.
- WhatsApp حسب وسائل متوافقة مع الشروط.
- قياس تكلفة واستضافة كل خدمة.

**القبول:** اختبار اتصال ووظيفة وصلاحيات لكل تكامل قبل تفعيله.

### Gate 7 — Admin Workbench
- لوحة مالك منفصلة.
- تعديل ومراجعة وإدارة وصيانة.
- صلاحيات دقيقة وسجل تدقيق.
- إيقاف وتراجع.

**القبول:** اختبارات صلاحيات وعزل وتدقيق واستعادة.

### Gate 8 — Release
- فحص أمني وأداء.
- اختبارات جوال وRTL/LTR.
- Backup/Restore.
- مراقبة وخطة Rollback.
- نشر تدريجي.

**القبول:** سجلات نشر ونتائج اختبار قابلة للمراجعة؛ لا يكفي نجاح build وحده.

## 18. تعليمات إلزامية لنماذج الذكاء الاصطناعي

عند استلام مهمة:
1. اقرأ تعليمات المستودع وملفات السياق والتسليم والتغيير.
2. اقرأ الوثيقة ذات الصلة وقواعد UX وعقد المهارة.
3. افحص الشجرة والفرع والـ diff والـ CI.
4. حدد معيار القبول والملفات ذات الصلة.
5. نفّذ أصغر تغيير آمن.
6. اختبر التغيير نفسه ثم الاختبارات والبناء المناسبين.
7. راجع diff والأسرار والملفات المولدة.
8. حدّث AI_HANDOFF وAI_CHANGELOG.
9. افتح PR للمراجعة ولا تدمج قبل اجتياز بوابة CI والمراجعة المطلوبة.
10. لا تدّعِ اختباراً بصرياً أو نشرًا لم يحدث.

تقرير التسليم يجب أن يذكر:
- الحالة: COMPLETE / PARTIAL / BLOCKED / NOT VERIFIED.
- التغييرات والملفات.
- الاختبارات ونتائجها الحقيقية.
- ما لم يتم اختباره.
- المخاطر والقيود.
- الخطوة التالية الواحدة.

**قرار التنفيذ:** ابدأ بإصلاح خط الأساس، ثم iAI وتجربة الجوال، ثم المهام والمكتبة، ثم Photo Studio وDealer Workspace، ثم طبقة التنفيذ والتكاملات، وأخيراً Workbench. لا تتجاوز البوابات ولا تعرض قدرات غير موصولة على أنها جاهزة.
