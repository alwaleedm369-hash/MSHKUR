# محرك مشكور الداخلي — المرحلة الثانية

## REA وMCP

REA في أدوات التطوير يعني Reverse Engineer Anything: أداة تحليل عكسي عبر MCP لدراسة البرامج والرحلات والسلوك مع الأدلة. لا تُشحن داخل runtime. أما محرك مشكور نفسه فيستخدم طبقات intent/extraction/policy/automation كمسار هندسي داخلي، وليست توسعة اسم REA.

## ما أصبح موجوداً في الكود

- SQLite محلي دائم مع WAL ومفاتيح أجنبية.
- تسجيل مستخدمين بكلمة مرور scrypt وجلسات HttpOnly.
- فصل مساحة كل معرض في السيارات والمهام والملفات والموافقات.
- ملفات الصور خارج قاعدة البيانات مع checksum وصلاحية وصول مرتبطة بالمعرض.
- سجل مهارات allowlist وملفات Agent Skills مستقلة.
- Maestro ينشئ jobs ويحفظ حالتها ويعيد queued عند إعادة تشغيل الخادم.
- محرك workflows يسجل run وsteps وينفذ سير عمل السيارة (validation ثم ad draft) داخل tenant واحد.
- مهارات محلية: مسودة إعلان من حقائق المستخدم، تدقيق سجل السيارة، تحسين صورة WebP، وطمس منطقة يحددها المستخدم.
- دفعات الصور تحفظ الأصل والنتيجة كأصلين منفصلين، وتعرض التقدم، وتسمح بالإيقاف بعد الصورة الجارية وإعادة محاولة العناصر المتعثرة فقط.
- إزالة خلفية داخل المتصفح عبر BG0/BiRefNet، مع تنزيل نموذج Lite عند أول استخدام. يلزم اختبار جودة فعلي قبل الإطلاق.
- ملفات موظفين متخصصين ومصنف نوايا عربي محدود.
- سجل موافقات للأفعال الخارجية وبصمة payload.
- adapter اختياري لنموذج محلي متوافق مع llama.cpp؛ لا يوجد fallback مدفوع.
- خادم MCP محلي عبر stdio، مع تحقق هوية owner/admin وتقييد الأدوات إلى معرض واحد.
- واجهة فعلية للتسجيل وإضافة السيارات وتجهيز الصور ومساعد تصنيف المهام.

## حدود المرحلة الحالية

المصنف حتمي وليس فهماً لغوياً عاماً. العامل داخل عملية Node واحدة وليس طابوراً موزعاً. إعادة محاولة دفعات الصور وإيقافها مضافة عبر API والواجهة. لم تكتمل دعوات الفريق أو صلاحيات متعددة المستخدمين أو Google OAuth أو WhatsApp أو MCP connectors أو Browser automation. الموافقة تسجل القرار ولا تنفذ فعلاً خارجياً حتى يتوفر الموصل المناسب.

## تخزين الصور

تُحفظ الملفات في `MSHKUR_STORAGE_DIR`، بينما يحتفظ SQLite بالمعرّف والنوع والحجم والبصمة فقط. يجب أن يكون هذا المجلد على قرص دائم. لا تضع الصور أو قاعدة البيانات داخل مجلد build المؤقت.


## دورة حياة مهام Maestro — تحديث

- حالات المهام المخزنة: queued, running, succeeded, failed, cancelled.
- إلغاء queued يوقفها فوراً. إلغاء running يعلّم طلب الإلغاء ويترك العملية المحلية الحالية تنتهي ثم يهمل ناتجها؛ لا يدّعي إيقاف المعالجة داخل مكتبة لا تدعم AbortSignal.
- إعادة المحاولة متاحة للمهام failed فقط، وتعيد استخدام سجل المهمة نفسه مع زيادة attempts، بحد أقصى ثلاث محاولات.
- عند بدء الخادم تُعاد المهام التي بقيت running إلى queued بعد انقطاع سابق، ثم تُستعاد جميع المهام المنتظرة على دفعات متتابعة.
- جميع عمليات القراءة والإلغاء وإعادة المحاولة مقيدة بـ tenant_id.
- لم تُنفذ pause/resume للمهام الجارية؛ لا تظهر كميزة جاهزة.
