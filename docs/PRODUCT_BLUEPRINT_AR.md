# MSHKUR — Product & Engineering Blueprint
## مرجع التنفيذ الموحد

تاريخ إعداد هذه الوثيقة: 2026-11-17

## 1. تعريف المنتج

MSHKUR منصة تشغيل متخصصة لإنجاز أعمال تجهيز السيارات والإعلانات من البداية إلى النهاية. ليست لوحة تحكم تقليدية ولا دليلاً لأدوات منفصلة. يدخل المستخدم من المهمة التي يريدها، وتبقى السيارة وملفاتها وسجل العمل هي السياق المشترك الذي يربط جميع الخطوات.

**الوعد الأساسي:** ابدأ من أي مهمة، ارفع الصور مرة واحدة، أنجز العمل على السيارة نفسها، راجع النتيجة، ثم احفظها أو صدّرها أو شاركها.

المنتج يبدأ بـ MSHKUR Cars ويُبنى بمحرك داخلي قابل لإضافة منتجات لاحقاً دون تحويل الواجهة إلى سوق أدوات مزدحم.

## 2. مبادئ تجربة المستخدم

- العربية RTL أولاً، Mobile-first، ثم دعم LTR.
- مساحة العمل نفسها هي الصفحة الرئيسية عند وجود مشروع/سيارة نشطة.
- لا لوحة إحصاءات كواجهة افتراضية، ولا صفحات تسويقية داخل التطبيق، ولا بطاقات SaaS عامة.
- الصورة والنتيجة أهم من الزخرفة؛ واجهة فاتحة هادئة، أسطح بيضاء، نص داكن، لون إبراز واحد، بلا ذهبي أو neon أو تدرجات متنافسة.
- قبل/بعد عنصر تفاعلي فعلي قابل للسحب، وليس صورتين ثابتتين.
- رفع → معالجة → مراجعة → تصدير مسار واحد متصل.
- شرح الوظيفة من خلال التفاعل؛ النصوص مقتضبة، ويمكن وضع التفاصيل في سطح مساعدة واحد.
- أهداف لمس لا تقل عن 44px، تباين واضح، حالات تركيز ولوحة مفاتيح وقارئ شاشة.
- لا نغيّر هوية السيارة أو شكلها لإنتاج صورة «أجمل». كل تعديل يجب أن يحافظ على السيارة الأصلية، ويُعرض بوضوح للمستخدم.

## 3. هيكل التنقل

### المستخدم الفردي
- **ابدأ / مساحة العمل:** تنفيذ سريع، السيارة الحالية، آخر نتيجة، ورفع الصور.
- **سياراتي:** سجل السيارات والمشاريع وألبومات الصور.
- **اكتشف:** مهام وأدوات متاحة، مجمعة حسب النتيجة لا حسب أسماء التقنيات.
- **أعمالي:** النتائج والملفات وسجل العمليات والتصدير.
- **المساعد:** طلب النتيجة باللغة الطبيعية ومتابعة المهام.

### المعرض / الفريق
- مساحة المعرض ومخزونه.
- أعضاء الفريق وأدوارهم.
- قوالب الإعلانات وهوية المعرض.
- العملاء والاستفسارات والمتابعة.
- تقارير الاستخدام والإنتاج.
- إعدادات الحساب والتكاملات.

تظهر الإدارة المتقدمة في مساحة منفصلة للمالك/المشرف، ولا تُفرض على المستخدم اليومي.

## 4. نموذج مساحة العمل الموحدة

كل سيارة تمثل مشروع عمل يحتوي على:
- بيانات السيارة ومصدر كل معلومة.
- الصور الأصلية غير القابلة للاستبدال.
- نسخ مشتقة لكل معالجة مع سجل parent/version.
- عمليات إزالة الخلفية والطمس والتحسين وتوحيد البيئة.
- مخرجات الإعلان والنصوص والكتالوج.
- موافقات المستخدم وسجل التنفيذ.
- التصديرات وروابط المشاركة والاستفسارات.

كل أداة تستقبل asset/project context الحالي. الانتقال إلى أداة أخرى لا يطلب رفع الصورة من جديد. لا تُكتب النتائج فوق الأصل؛ كل نتيجة مشتقة تحفظ كنسخة مستقلة ويمكن الرجوع عنها.

## 5. رحلة تجهيز السيارة

1. إضافة سيارة أو اختيار سيارة موجودة.
2. رفع مجموعة صور أو التقاطها (الحد الأقصى يُضبط من إعدادات الخادم، والدفعات تُعالج على مراحل).
3. تصنيف الصور وترتيبها واختيار الصورة الرئيسية.
4. تنفيذ الأدوات المطلوبة:
   - إزالة الخلفية.
   - بيئة تصوير موحدة (أبيض/رمادي/داكن).
   - طمس اللوحة يدوياً، ثم كشف تلقائي فقط بعد اختبار دقته.
   - تحسين الإضاءة والتباين والحدة دون تغيير تفاصيل السيارة.
   - تظليل الزجاج والظلال كطبقات قابلة للمعاينة، لا كادعاء أنها تعمل قبل تنفيذها.
5. مراجعة كل صورة عبر Before/After.
6. فحص الجودة: الدقة، الحواف، بقاء أجزاء السيارة، عدم وجود تشوه، خصوصية اللوحة.
7. إصلاح أو إعادة المحاولة عند الفشل، دون فقد الأصل.
8. إنشاء مسودة الإعلان من بيانات موثقة فقط؛ الحقول الناقصة تظهر للمستخدم ولا تُخمن.
9. إنشاء حزمة تصدير: الصور، ZIP، كتالوج PDF، نصوص جاهزة للمنصات.
10. مشاركة المستخدم أو نشره بعد موافقته.

## 6. المحرك والعمالة الذكية

### Maestro — المدير المركزي
- تحليل نية المستخدم.
- تحويل الطلب إلى خطة ومهام typed.
- اختيار skill/agent المناسب حسب المدخلات والقدرات والخصوصية والترخيص والتكلفة.
- تنفيذ المهام المستقلة بالتوازي عند الحاجة.
- حفظ حالة كل خطوة ومدخلاتها ومخرجاتها.
- التحقق من النتيجة وتجميع مخرج واحد.
- إظهار ما فُهم وما تم وما يحتاج المستخدم إليه.
- تسجيل الزمن والموارد والتكلفة الفعلية عند توفرها.
- إعادة المحاولة بأمان وإيقاف المهمة عند الحاجة.

### الموظفون المتخصصون
أدوار مقترحة قابلة للتشغيل عند الطلب:
- مدير تجهيز السيارة.
- مصور/موجه زوايا التصوير.
- خبير الصور والخلفيات.
- خبير خصوصية اللوحات.
- مراقب جودة الصور.
- كاتب إعلان السيارات.
- مدقق بيانات السيارة.
- منسق المعرض والمخزون.
- مدير العملاء والاستفسارات.
- موظف Google Workspace.
- موظف النشر والمشاركة.

الوكيل تعريف (تعليمات + skills + tools + permissions + model policy)، وليس عملية تعمل 24/7. لا تنشأ agent runtime إلا عند وجود مهمة.

## 7. سجل المهارات وAI Workforce Studio

كل skill يجب أن تحتوي على:
- id/name/version/description.
- المدخلات والمخرجات مع JSON Schema.
- أنواع الملفات وحدود الحجم.
- handler أو MCP tool أو browser recipe معزول.
- الأذونات المطلوبة.
- سياسة الموافقة.
- الترخيص والمصدر والإصدار.
- هل يعمل محلياً أو يحتاج خدمة خارجية.
- تقدير الموارد والوقت والتكلفة.
- اختبارات وقواعد قبول ومخاطر.
- شروط retry/idempotency.

طرق الإضافة:
1. قوالب مهارات داخلية.
2. استيراد Agent Skills بعد فحص الملفات.
3. استيراد MCP server بعد مراجعة المصدر والأذونات.
4. Workflow Builder لتوصيل مهارات موجودة.
5. Skill Creator ينشئ مسودة فقط، ثم lint + sandbox tests + مراجعة بشرية + اعتماد.

لا يتم تشغيل كود مستورد أو مولّد في عملية الخادم الرئيسية. يُعزل التنفيذ، وتُمنع الأسرار والاتصالات الشبكية غير المصرح بها، ويُقيد الوصول إلى الملفات حسب المهمة.

## 8. Universal Connectivity Engine

ترتيب اختيار طريقة التنفيذ:
1. مكتبة محلية مفتوحة المصدر مرخصة ومختبرة.
2. API رسمي عندما يكون مطلوباً ومسموحاً.
3. MCP server موثوق وصلاحياته محدودة.
4. Playwright للتدفقات الحتمية المسموح بها.
5. Stagehand/Browser agent للصفحات التي تحتاج فهماً، بعد توفير نموذج محلي/معتمد.
6. مساعدة المستخدم عندما يلزم تسجيل دخول أو MFA أو CAPTCHA أو موافقة.

لا نتجاوز CAPTCHA أو paywall أو سياسات المواقع أو حدود الوصول. لا نفترض أن أتمتة المتصفح مسموحة في أي موقع. لا نرسل كلمات مرور المستخدم إلى وكيل أو skill.

## 9. REA وMCP

- REA (Reverse Engineer Anything) أداة تطوير/بحث لتحليل البرامج والمواقع التي نملك صلاحية فحصها، وتوثيق الأدلة والسلوك. ليست محركاً تشغيلياً في الإنتاج، ولا تستنسخ العلامات أو الأصول أو الشيفرة المحمية.
- MCP هو بروتوكول موحد لعرض أدوات وموارد للمساعدين. لكل server قائمة أدوات واضحة، schema، صلاحيات، حدود، مهلة، وسجل.
- خادم MCP المحلي الحالي عبر stdio نقطة بداية. بوابة بعيدة مستقبلية تتطلب مصادقة قوية، عزل tenant، موافقات، ومراجعة أمنية.
- لا يثبت أي MCP server تلقائياً في بيئة الإنتاج.

## 10. النماذج المحلية وتقليل التكلفة

- معالجة الصور المحلية في المتصفح هي الخيار الأول عندما تكون عملية وآمنة.
- BG0/BiRefNet Lite ينزل عند أول استخدام (قرابة 98.5MB حسب ملف المشروع)، ثم يُخزن في المتصفح؛ لا يعني ذلك أن النموذج مضمن داخل ZIP.
- ضغط ONNX وGGUF أدوات بناء/مختبر وليست ميزات تشغيل تلقائية.
- نموذج المحادثة المحلي اختياري ويحتاج اختبار الذاكرة والسرعة والدقة على جهاز/خادم محدد. لا نضع أوزان LLM كبيرة في ZIP دون تحقق من الحجم والترخيص والعتاد.
- لا يوجد cloud fallback مدفوع صامت. عند غياب نموذج محلي، تظل الوظائف المحددة rule-based أو تُعرض كغير متاحة.
- لا نعد بإزالة خلفية أو كشف لوحة أو تظليل أو توليد ظل قبل اختبار صور متنوعة وأجهزة حقيقية.

## 11. Google Workspace Hub

ربط Google اختياري ومفصول عن المنتج الأساسي:
- Google Identity/OAuth: تسجيل دخول بموافقة المستخدم وصلاحيات محددة.
- Drive: حفظ مجلدات وملفات التصدير في حساب المستخدم.
- Sheets: تقارير ومزامنة بيانات اختيارية، وليست قاعدة البيانات الأساسية.
- Docs: كتالوجات وتقارير.
- Gmail/Calendar/Contacts: لا تُطلب إلا عند إطلاق ميزة تحتاجها وبأقل scopes ممكنة.
- Maps: روابط أو خرائط تفاعلية بحسب الخدمة والحصص والتكلفة.
- Gemini: مساعد خارجي اختياري؛ لا يُستدعى في المسار الأساسي دون تفعيل المستخدم وتحديد حدود الاستخدام.

Google AI Studio ليس أداة تصميم للمنتج. يمكن استخدامه لاحقاً كمكان إعداد/اختبار تكاملات Google عند الحاجة فقط.

## 12. WhatsApp والتواصل

الأساس المجاني:
- إنشاء نصوص ورسائل جاهزة محلياً.
- توليد رابط wa.me يفتح تطبيق المستخدم مع النص المجهز.
- مشاركة الملفات من جهاز المستخدم عندما يدعم المتصفح ذلك.
- حفظ قوالب متابعة العملاء وسجل ما أعده المستخدم.

الإرسال الآلي عبر WhatsApp Business Platform أو مزود خارجي ميزة اختيارية منفصلة؛ لا تُوصف بأنها مجانية أو غير محدودة. تتطلب موافقة المستخدم، وإعداد حساب رسمي، والتحقق من سياسة الرسائل والتسعير الحالي.

## 13. البيانات والأمان

- عزل صارم لكل مستخدم/معرض tenant.
- ملفات الأصل والنتائج في storage مستقل مع checksum وmetadata.
- لا تُحفظ الصور الثنائية داخل SQLite.
- تشفير النقل، جلسات آمنة، rate limits، CSRF/Origin protection، صلاحيات RBAC.
- سجل تدقيق لكل عملية مهمة.
- موافقة صريحة للنشر والإرسال والشراء والحذف.
- تصدير وحذف بيانات المستخدم وفق سياسات واضحة ومتطلبات PDPL.
- نسخ احتياطي دوري واختبار استعادة قبل الإنتاج.
- لا ترفع صور العملاء إلى خدمة خارجية دون بيان واضح وموافقة.

## 14. التسعير المقترح

لا نبيع أسماء الأدوات؛ نبيع إنجاز العمل:
- مجاني/تجريبي: تجربة الأدوات المحلية مع حدود منصفة على التخزين والدفعات.
- فرد: مساحة سيارات ونتائج وتصدير أكثر.
- معرض: مخزون وفريق وقوالب وهوية وإدارة استفسارات.
- معرض Pro: دفعات أكبر، صلاحيات وتقارير وتكاملات موسعة.
- خدمات خارجية: تُحسب منفصلة عند وجود تكلفة حقيقية (رسائل WhatsApp أو API مدفوع أو تخزين خارجي).

يجب أن يكون القياس بحسب موارد فعلية (دقائق معالجة/حجم تخزين/عمليات مدفوعة) لا رصيداً غامضاً. لا نعتمد أسعاراً نهائية قبل قياس التكلفة الحقيقية.

## 15. خارطة التنفيذ

### المرحلة A — الأساس
- واجهة task-first ومساحة سيارة موحدة.
- تسجيل محلي وtenant isolation.
- رفع الصور وتخزين النسخ.
- إزالة خلفية محلية وطمس يدوي وتحسين WebP.
- بيانات السيارة ومسودة الإعلان.
- اختبارات وCI وZIP source package.

### المرحلة B — استوديو السيارة
- batch jobs وqueue وحدود موارد.
- gallery + before/after + undo/versioning.
- جودة الصور وحالات الخطأ.
- PDF/ZIP export حقيقي.
- تصنيف الصور واختيار الصورة الرئيسية.

### المرحلة C — المنتج التجاري للمعارض
- مخزون وعملاء واستفسارات.
- عضويات وأدوار ودعوات.
- صفحات عرض عامة وQR.
- قوالب الإعلان والمشاركة.

### المرحلة D — Workforce
- skill schemas وagent profiles.
- workflow DAG مع retries/idempotency.
- Mission Control وApproval Center.
- MCP registry وsandboxed skill import.
- اختبارات أمنية وتدقيق تراخيص.

### المرحلة E — التكاملات
- Google OAuth/Drive/Sheets/Maps بحسب الأولوية.
- Gemini اختياري.
- WhatsApp click-to-chat أولاً، ثم Business Platform إذا وافق المستخدم على تكلفته.
- Browser automation المصرح به فقط.

### المرحلة F — الإنتاج والتوسع
- نسخ احتياطي واستعادة مجربة.
- مراقبة وأداء وقياس تكلفة.
- نشر على استضافة تدعم Node.js وقرصاً دائماً.
- مراجعة PDPL وأمن واختبارات أجهزة فعلية.

## 16. معايير قبول كل مرحلة

- الوظيفة حقيقية وليست زرّاً شكلياً.
- اختبارات unit/API/integration ناجحة.
- typecheck وbuild ناجحان.
- حالات الفشل وإعادة المحاولة موثقة.
- لا أسرار أو بيانات مستخدم في Git أو ZIP.
- التراخيص ومصادر الأوزان واضحة.
- قياس الذاكرة/الوقت على أجهزة حقيقية للميزات الثقيلة.
- لا تدمج إلى main قبل مراجعة PR ونجاح CI.

## 17. حدود النسخة الحالية

الفرع الحالي يضم أساساً أولياً لواجهة RTL وPWA، حسابات محلية، SQLite، سيارات، ملفات، مهارات محدودة، Maestro أولي، workflow لمسودة إعلان، BG0 لإزالة الخلفية، طمس مستطيل يدوي، وMCP محلي عبر stdio.

لا تزال Google OAuth، WhatsApp، النشر المباشر، كشف اللوحات تلقائياً، تظليل الزجاج والظلال، workflow DAG عام، browser agents، LLM محلي جاهز، النسخ الاحتياطي واختبارات الإنتاج غير مكتملة. لا تُعرض هذه العناصر للمستخدم على أنها تعمل قبل بنائها واختبارها.

## 18. تعليمات الاستيراد إلى Google AI Studio

استورد مجلد المشروع/ZIP كمصدر كود فقط إذا كانت بيئة AI Studio تدعم نوع المشروع. لا تطلب منه إعادة تصميم الواجهات أو إعادة كتابة المشروع. اطلب منه مراجعة تكاملات Google فقط، والحفاظ على React/TypeScript وExpress وSQLite والـskills/workflows، وعدم حذف أو استبدال أي وظيفة محلية. يجب تنفيذ OAuth عبر الخادم، واستخدام scopes محدودة، وعدم وضع الأسرار في الواجهة أو المستودع.
