# تصور مركز المهارات والإضافات — MSHKUR / iAI

> الحالة: تصور UI/UX ومواصفات منتج أولية — غير منفذ في التطبيق بعد.
> تاريخ الإعداد: 27 نوفمبر 2026.
> مصدر قائمة الأدوات والمهارات: وصف المالك في المحادثة. أسماء المنتجات والأوصاف أدناه منقولة كما وردت، ولم تُجرَ بعد مراجعة مستقلة للتراخيص أو الأسعار أو قدرات التكامل.

## 1. الرؤية

إنشاء مركز عمل موحد يتيح للمالك إدارة قدرات النظام، بينما يرى المستخدم النهائي تجربة بسيطة قائمة على المهمة والنتيجة. لا نعرض للمستخدم أسماء الوكلاء أو المهارات الداخلية أو تفاصيل MCP والموصلات إلا عند الحاجة الإدارية.

المبدأ:
- **Skill / مهارة:** منطق أو إجراء متخصص ينفذه النظام لتحقيق هدف.
- **Extension / إضافة:** تطبيق أو خدمة خارجية توفر قدرة قابلة للاتصال.
- **Workflow / سير عمل:** ترتيب عدة مهارات وإضافات وموافقات لإكمال مهمة.
- **Agent / وكيل:** منفذ مستقل ضمن سير العمل، بصلاحيات وحدود واضحة.
- **Admin Workbench / مكتب الإدارة:** مساحة المالك لمراجعة التثبيت والصلاحيات والتكلفة والتنفيذ.

لا يعني إدراج أداة في هذا التصور أنها متصلة أو مجانية فعلياً أو مرخصة للاستخدام التجاري. يلزم التحقق من المستودع الرسمي، الترخيص، الاستضافة، المتطلبات، الأمان، والتكلفة قبل اعتمادها.

## 2. بنية المعلومات (Information Architecture)

### واجهة المستخدم
1. **مساحة العمل:** ابدأ مهمة، ارفع ملفات، تابع النتيجة.
2. **المهام الجاهزة:** قوالب مثل إنشاء فيديو، تحويل صوت إلى نص، إدارة مشروع، وتحليل فكرة.
3. **المخرجات:** ملفات ونتائج وسجل مختصر لما تم.
4. **المساعدة:** توضيح ما يحتاجه المستخدم فقط، دون كشف أسماء المحركات الداخلية.

### مكتب المالك
1. **نظرة عامة:** حالة النظام، المهام الجارية، التنبيهات.
2. **مكتبة المهارات:** بحث وتصنيف وتفاصيل وإصدارات.
3. **مركز الإضافات:** موصلات متاحة، حالة الربط، الأذونات.
4. **منشئ سير العمل:** ترتيب الخطوات والشروط والموافقات.
5. **الوكلاء:** تعريف الدور والنطاق والأدوات المسموحة.
6. **الموافقات:** طلبات الوصول والتنفيذ عالي الأثر.
7. **سجل التشغيل:** المدخلات المرجعية، الخطوات، المخرجات، الأخطاء، والتكلفة.
8. **الأمان والتكلفة:** الأسرار، الصلاحيات، حدود الاستخدام، وسياسات الاحتفاظ.

## 3. مجموعات الإضافات المرشحة من قائمة المالك

هذه قائمة مرشحة للتقييم والربط، وليست قائمة تكاملات مكتملة:

| الاسم كما ورد | الاستخدام المقترح داخل النظام | مجموعة الواجهة |
|---|---|---|
| Open HeyField | إنشاء فيديوهات بالذكاء الاصطناعي | الفيديو والإبداع |
| Voice Studio | توليد الأصوات محلياً | الصوت |
| Open SEO | متابعة ترتيب الموقع وتدقيق الروابط الخلفية والأداء | التسويق وSEO |
| AppFlowy | مساحة معرفة وملاحظات مع نماذج AI محلية | المعرفة والعمل |
| Open Whisper | تحويل الكلام إلى نص | الصوت والإدخال |
| OpenProject | إدارة المشاريع والمهام | إدارة العمل |
| Cotdy | حجز المواعيد وتنظيم الجداول | الجدولة |
| Chatwoot | صندوق وارد موحد لمحادثات العملاء | خدمة العملاء |
| Cap | تسجيل الشاشة ومشاركة الفيديو | التسجيل والتوثيق |

لكل إضافة بطاقة تتضمن:
- الاسم والوصف الوظيفي المختصر.
- الفئة، مصدر المشروع الرسمي، ونوع الاستضافة (محلي/خادم/سحابي) بعد التحقق.
- حالة التقييم: **مرشح / قيد الفحص / معتمد / متصل / متوقف / مرفوض**.
- حالة الترخيص وآخر تاريخ مراجعة.
- الصلاحيات المطلوبة والبيانات التي يمكنها الوصول إليها.
- التكلفة المتوقعة وحدود الاستخدام، إن وجدت.
- طريقة الربط، مالك الاتصال، وآخر اختبار ناجح.
- إجراءات التفعيل والإيقاف وفصل الاتصال.

## 4. مكتبة Founder Skills

وصف المالك حزمة Founder Skill على Claude على أنها تضم 11 مهارة لاختبار وتقييم جدوى المشاريع. التفاصيل التي وصلت حتى الآن تصف أربع مهارات فقط؛ لا نخترع أسماء أو وظائف للمهارات السبع الأخرى، وتظل **غير موصوفة / بانتظار المصدر**.

### المهارات الموصوفة

1. **مهارة مجلس الإدارة:** محاكاة وجهات نظر وتوجيهات رواد أعمال بارزين لتقديم استشارات للفكرة. يجب أن تعرض المحاكاة كأدوار افتراضية لا كاستشارات حقيقية صادرة عن الأشخاص.
2. **مهارة مدير التسويق:** تخطيط الإطلاق ووضع خطة تسويق.
3. **مهارة المدير المالي:** تحليل نموذج الإيرادات وحساب هوامش الربح وفق افتراضات ومدخلات واضحة.
4. **مهارة المستهلك (Consumer Skill):** تشغيل وكلاء يمثلون شرائح عملاء مختلفة، واختبار الفكرة عبر 100 سيناريو شراء وفق الوصف المقدم، لاستخراج نسب النجاح والاعتراضات. النتائج محاكاة وليست دليلاً على طلب سوقي فعلي أو مقابلات عملاء حقيقية.

### متطلبات توثيق كل مهارة
- الهدف، المدخلات، المخرجات، خطوات التنفيذ.
- حدود المعرفة والافتراضات ومصادر البيانات.
- الأدوات/الإضافات التي تحتاجها.
- صلاحياتها، مستوى المخاطر، وتكلفة التشغيل.
- حالات الاختبار ومعايير النجاح والفشل.
- إصدار المهارة، سجل التغيير، ومالك الاعتماد.

## 5. سيناريو تجربة المستخدم (Happy Path)

1. يكتب المستخدم: «قيّم فكرة مشروعي وجهز خطة إطلاق».
2. يطلب النظام الحد الأدنى من المعلومات الناقصة.
3. ينشئ خطة عمل ظاهرة للمستخدم: تحليل الفكرة، اختبار شرائح العملاء، تقدير الإيرادات، وخطة التسويق.
4. يختار المنسق المهارات المعتمدة داخلياً؛ لا تظهر أسماءها التقنية في الواجهة العادية.
5. إذا تطلبت خطوة إضافة خارجية أو مشاركة بيانات، يوضح النظام ما سيُرسل ولمن، ويطلب موافقة صريحة.
6. تنفذ الخطوات، وتظهر حالة كل خطوة: قيد التنفيذ، تحتاج موافقة، مكتملة، أو تعذرت.
7. تعرض لوحة النتائج ملخصاً وفرضيات ومخاطر وتوصيات، مع تمييز المحاكاة عن البيانات الواقعية.
8. يحفظ سجل التنفيذ في مساحة المشروع، ويتيح للمالك مراجعته.

## 6. تصور الواجهات

### A. واجهة المستخدم — مساحة العمل
- شريط علوي هادئ: اسم مساحة العمل والتنبيهات والحساب؛ لا يعرض أسماء المهارات الداخلية.
- عنوان رئيسي يركز على المهمة: «ما الذي تريد إنجازه؟».
- حقل طلب واضح مع إرفاق ملفات.
- بطاقات مهام جاهزة مختصرة: «اختبر فكرة مشروع»، «أنشئ فيديو»، «حوّل صوتاً إلى نص»، «نظّم مشروعاً».
- مساحة تقدم تعرض الخطوات بلغة بشرية.
- لوحة نتائج تحفظ المخرجات والملفات والملخص.

### B. مكتب المالك — مركز المهارات والإضافات
- تبويبان رئيسيان: **المهارات** و**الإضافات**.
- شريط بحث وفلاتر حسب الفئة والحالة ومستوى المخاطر.
- بطاقة كل عنصر: الاسم، وصف من سطر واحد، الحالة، الإصدار، آخر فحص، وزر «التفاصيل».
- صفحة التفاصيل مقسمة إلى: نظرة عامة، المتطلبات، الصلاحيات، الاختبارات، السجل.
- أزرار الإدارة: «تقييم»، «تفعيل»، «إيقاف»، «تحديث»، «عرض السجل». لا يظهر زر التفعيل قبل استيفاء فحوص الاعتماد.

### C. منشئ سير العمل
- محرر خطوات متتابعة بترتيب واضح.
- كل خطوة تعرض: المهمة، المهارة/الإضافة المستخدمة (للمالك فقط)، المدخلات، المخرجات، وشرط الانتقال.
- دعم نقاط موافقة قبل إرسال البيانات أو تنفيذ فعل خارجي.
- لوحة جانبية لاختبار سير العمل ببيانات تجريبية.
- حفظ كمسودة قبل النشر، مع سجل نسخ وإمكانية الرجوع.

### D. شاشة الموافقة
تعرض بوضوح: الإجراء المطلوب، سبب الحاجة، البيانات التي ستُشارك، الخدمة المستقبلة، الأثر المتوقع، والتكلفة/الحد إن كان معروفاً. الخيارات: «موافقة لهذه المرة»، «رفض»، و«مراجعة الصلاحيات». لا تستخدم موافقة عامة مبهمة.

## 7. مبادئ التصميم المرئي والتفاعل

- تصميم Mobile-first مع تخطيط متجاوب لسطح المكتب.
- واجهة عربية RTL أصيلة، مع دعم LTR للإنجليزية.
- خلفيات محايدة، تباين جيد، ومساحات بيضاء منضبطة.
- بطاقات بسيطة، أيقونات مفهومة، وشارات حالة غير مبالغ فيها.
- لا تستخدم رسوم زخرفية توحي باتصال أو نجاح غير حقيقي.
- حالات واضحة: فارغ، تحميل، نجاح، فشل، غير متصل، يحتاج إعداداً، يحتاج موافقة.
- دعم لوحة المفاتيح والتركيز المرئي وتقليل الحركة.
- رسائل قصيرة تشرح للمستخدم ما يحتاج فعله الآن فقط.

### ترتيب الهاتف
1. عنوان الصفحة والبحث.
2. تبديل المهارات/الإضافات.
3. فلاتر قابلة للطي.
4. قائمة البطاقات عمود واحد.
5. تفاصيل العنصر في صفحة أو لوحة مستقلة؛ تجنب الأعمدة الضيقة.

### ترتيب سطح المكتب
- شريط تنقل جانبي.
- منطقة مركزية للبحث والقائمة.
- لوحة تفاصيل اختيارية على الجانب عند توفر مساحة.
- لا تترك مساحة فارغة كبيرة ولا تضغط منطقة العمل.

## 8. دورة حياة المهارة والإضافة

**اكتشاف → فحص المصدر والترخيص → مراجعة الأمن → إعداد بيئة اختبار → اختبار الوظيفة → مراجعة الصلاحيات والتكلفة → موافقة المالك → تفعيل محدود → مراقبة → تحديث/إيقاف.**

لا تُمنح أي إضافة وصولاً شاملاً افتراضياً. استخدم أقل صلاحية ممكنة، خزّن الأسرار خارج الواجهة ومستودع المصدر، ووفّر إلغاء الاتصال وحذف بيانات الاعتماد.

## 9. الأمن والحوكمة

- لا تحفظ مفاتيح API أو كلمات المرور في كود الواجهة أو ملفات Git.
- فصل صلاحيات المستخدم والوكيل والمهارة والإضافة.
- موافقة صريحة على إرسال بيانات إلى خدمة خارجية.
- تقييد الوصول إلى الملفات والمجلدات حسب المهمة.
- سجل تدقيق لا يسجل الأسرار أو محتوى حساساً بلا ضرورة.
- حدود زمنية ومالية ومعدلات استخدام لكل مهمة.
- تشغيل الأدوات الخارجية في بيئة معزولة مع تحقق من المخرجات.
- إيقاف فوري للإضافة عند اكتشاف سلوك غير متوقع.
- لا تُعامل مخرجات الوكلاء أو المحتوى القادم من الأدوات كتعليمات موثوقة.

## 10. مراحل التنفيذ المقترحة

### المرحلة 0 — تصميم واعتماد
- اعتماد بنية المعلومات وتدفقات الاستخدام.
- رسم حالات الهاتف وسطح المكتب.
- توحيد حالات العناصر وبطاقاتها.
- اعتماد نموذج الصلاحيات والموافقات.

### المرحلة 1 — واجهة إدارية ببيانات تجريبية
- مركز المهارات والإضافات.
- صفحات التفاصيل والبحث والتصفية.
- سجل تشغيل تجريبي.
- لا توجد اتصالات فعلية بالخدمات بعد.

### المرحلة 2 — إطار تشغيل المهارات
- تعريف Manifest موحد للمهارات.
- سجل إصدارات واختبارات.
- منفذ مهام مع سجل نتائج.
- موافقات وحدود استخدام.

### المرحلة 3 — إضافة موصل واحد تجريبياً
- اختيار موصل واحد بعد فحص الترخيص والأمن.
- اختبار داخل بيئة محدودة.
- توثيق الأداء والأخطاء والتكلفة قبل التوسع.

### المرحلة 4 — Founder Skills
- تنفيذ المهارات الأربع الموصوفة أولاً بعد تحديد مصادرها ومطالباتها وحدودها.
- إبقاء المهارات السبع الأخرى غير مفعلة حتى توفير مواصفاتها.
- اختبار Consumer Skill مع توضيح أن السيناريوهات محاكاة.

## 11. معايير القبول

- يستطيع المالك البحث عن مهارة أو إضافة ومعرفة حالتها دون التباس.
- لا يظهر عنصر على أنه متصل قبل نجاح اختبار اتصال موثق.
- لا يمكن تفعيل إضافة تتطلب صلاحيات غير معتمدة.
- يرى المستخدم تقدماً ومخرجات مفهومة دون كشف البنية الداخلية.
- تظهر موافقة صريحة قبل مشاركة بيانات خارجية أو تنفيذ فعل ذي أثر.
- يمكن إيقاف الاتصال وإبطال بيانات الاعتماد.
- تُعرض نتائج Founder Skills على أنها تحليل/محاكاة مع ذكر الافتراضات.
- تعمل الواجهة على الهاتف وRTL وLTR، مع حالات التحميل والفشل والفراغ.
- لا يُعلن عن تكامل أو توفير تكلفة أو ترخيص مجاني قبل التحقق من المصدر الرسمي.

## 12. نقاط مفتوحة قبل التنفيذ البرمجي

1. التحقق من التهجئة والمستودع الرسمي والترخيص لكل إضافة في القائمة.
2. تحديد المقصود الدقيق بـ Open HeyField وCotdy وروابطهما الرسمية.
3. توفير أسماء ووصف المهارات السبع غير المفصلة من Founder Skill.
4. تحديد هل مركز المهارات والإضافات جزء من MSHKUR فقط أم من طبقة iAI المشتركة.
5. تحديد بيئة التشغيل المستهدفة: محلي، خادم خاص، أم خدمات مستضافة.
6. مراجعة بنية المشروع الحالية قبل اختيار نقطة دمج الواجهة أو أي Backend.
