# دفتر التفكيك الهندسي والبحث التطبيقي — MSHKUR

> بروتوكول مستمر لدراسة المنتجات والتطبيقات والوثائق والمستودعات، واستخراج الوظائف القابلة لإعادة البناء بصورة مستقلة. لا يعني هذا الملف أن المصادر المدرجة قد اختُبرت أو أن وظائفها أصبحت متاحة في MSHKUR.

## 1) الهدف
بناء محرك متخصص في صور السيارات وإعلاناتها، عبر فهم الأنظمة المرجعية وتفكيكها إلى:
- رحلة المستخدم (UX) وسياق المهمة.
- المدخلات، القيود، ومخرجات العمل.
- الخوارزمية/النموذج/الاعتماديات المحتملة.
- معالجة الحواف والفشل والرجوع والتصحيح.
- الأداء والذاكرة والأجهزة.
- الترخيص للكود والأوزان والبيانات والأصول.
- اختبارات قبول مستقلة داخل MSHKUR.

## 2) المصادر وحدود التحليل
الأولوية للمصادر المصرح بها: مستودعات مفتوحة المصدر، الوثائق الرسمية، ملفات SDK، الديمو العام، التطبيقات التي يملكها الفريق أو يحق له فحصها، وصور/عينات اختبار مرخصة.
مسموح: تحليل الواجهات والسلوك العام، قراءة الوثائق وملفات المصدر، مراجعة بنية الحزم، تحليل تدفقات الشبكة في بيئة نملكها أو مصرح لنا بها، تحليل static/dynamic للأجزاء المتاحة قانونياً، وقياس النتائج على fixtures.
ممنوع: تجاوز الوصول أو الحماية، استخراج أسرار أو بيانات مستخدمين، تخطي CAPTCHA/DRM، نسخ الأصول أو العلامات أو الكود المحمي، أو إدخال كود مجهول إلى runtime.

## 3) بطاقة دراسة المصدر
لكل مصدر نسجل:
- الاسم، URL، نوع المصدر، تاريخ الدراسة.
- إصدار/commit/نسخة التطبيق.
- LICENSE وحقوق الأوزان/البيانات/الأصول والتبعيات.
- الوظيفة المحددة المراد فهمها (لا دراسة عامة مبهمة).
- خطوات الرحلة مع لقطات أو ملاحظات.
- المدخلات/المخرجات/القيود/الأخطاء.
- الأدلة والمراجع المباشرة.
- الفرضيات التي لم يتم التحقق منها.
- تصميم إعادة التنفيذ داخل MSHKUR.
- اختبار قبول، benchmark، وحالة القرار: study / prototype / approved / hold / reject.

## 4) خط تحليل التطبيقات
1. تحديد سؤال واحد قابل للقياس.
2. جمع الوثائق الرسمية وREADME والـAPI/SDK والـLICENSE وmodel card.
3. توثيق الرحلة: input → action → intermediate states → output → recovery.
4. دراسة المصادر/الاعتماديات المتاحة دون استخراج بيانات خاصة.
5. رسم pipeline وفصل كل مرحلة عن غيرها.
6. إنشاء prototype مستقل باستخدام fixtures.
7. قياس الجودة والسرعة والذاكرة وحالات الفشل.
8. مراجعة الأمان والخصوصية والترخيص.
9. تحويل النتيجة إلى skill spec وtests وADR.
10. الدمج بعد review فقط.

## 5) حزم الدراسة لمحرك السيارات
### A. Segmentation / Background removal
قارن mask coverage، تفاصيل الحواف (الشبك، المرايا، العجلات، الشعر/الفراغات غير relevant)، shadow preservation، transparent output، زمن/ذاكرة، وحالات الخلفية المعقدة. لا تختزل النتيجة إلى score واحد.

### B. Plate privacy
Detector → confidence → region proposal → user correction → blur/pixelate/opaque → coverage validator. لا تعتمد كشف اللوحة وحده: يجب أن تكون هناك مراجعة ومقارنة على كل لوحة، بما فيها لوحات أمامية/خلفية، زوايا، انعكاس، لوحات جزئية، أو أكثر من لوحة. عند الشك، اعرض تحذيراً أو fallback يدوي.

### C. Glass tint
منطقة الزجاج/قناع → اختيار tint → تعديل اللون مع المحافظة على الانعكاسات والحدود والملمس → before/after. لا تغيّر لون أجزاء السيارة خارج mask، ولا تعتبر Polygon اليدوي كشفاً تلقائياً.

### D. Lighting / color
تقييم exposure، highlights، shadows، white balance، saturation، local contrast. الحفاظ على اللون الحقيقي للسيارة ومنع القصّ أو التحول غير الطبيعي. توفير reset/undo.

### E. Scene / shadow
قص السيارة → scene matching (scale، perspective، horizon، light direction) → contact shadow/reflection → composite → edge QA. تجنب تغيير شكل السيارة أو إخفاء تفاصيلها؛ خلفيات آمنة تجارياً، مع قوالب مرخصة.

### F. Output / QA
حفظ الأصل، مشتقات versioned، format/dimensions/quality profiles، metadata policy، checksums، preview، batch status، failed-item retry، and export. اختبار على أجهزة ضعيفة وذاكرة محدودة.

## 6) نموذج Skill Manifest المقترح
- id / name / version / description
- input schema / output schema
- runtime & dependencies
- model & weight source / revision / checksum
- licenses / notices
- capability flags / resource limits
- permission boundary
- deterministic vs stochastic
- validation / error taxonomy / retry policy
- fixture tests / benchmark / quality gate
- reviewer / status / release date

## 7) سجل الدراسات
| المصدر/المجال | السؤال | الحالة | القرار/النتيجة |
|---|---|---|---|
| BG0 / BiRefNet | إزالة الخلفية محلياً في المتصفح | مدمج، جودة الإنتاج غير محسومة | قياس الجودة والاعتمادية والترخيص قبل إطلاق |
| OpenCV | عمليات CV التقليدية وmask geometry | مرجع محتمل | دراسة محددة الوظائف قبل إضافة الاعتماد |
| SAM 2 | تصحيح masks/interactive segmentation | مرشح دراسة | لا اعتماد حتى benchmark والترخيص/البيئة |
| rembg | مقارنة pipelines وmodel adapters | مرجع | مراجعة الأوزان منفصلة عن الكود |
| lightScout/light-converter | تحرير masks وbatch UX | دراسة مسجلة | لا نسخ كود/weights دون مراجعة |
| lumacut | mask editing/restoration UX | دراسة مسجلة | استخراج أنماط سلوكية فقط |
| Spyne / CarFlow / carbg.ai | تجربة العرض التجاري/التحضير | benchmark UX فقط | تحليل واجهة وسلوك عام؛ لا نسخ أصول أو كود |
| REA | تحليل مصادر وواجهات مصرح بها | أداة تطوير | خارج runtime |

## 8) بوابات إطلاق المحرك
- لا إطلاق دون اختبار قابل للتكرار على مجموعة صور مرخصة.
- لا ادعاء كشف تلقائي إذا كانت الوظيفة يدوية.
- لا خدمة API مدفوعة شرطاً للمسار الأساسي.
- لا استبدال للأصل؛ كل تحرير مشتق مستقل.
- لا موافقة على نموذج بناء على اسم المكتبة وحده.
- لا قبول لنتيجة غير قابلة للتراجع أو التصحيح.
- لا تنفيذ تلقائي لكود مستورد.
- توثيق قيود الأجهزة، الحجم، الذاكرة، الزمن، وأخطاء التشغيل.

## 9) الخطوة التنفيذية التالية
Audit للمسار الفعلي داخل المستودع: GuestStudio / CarAdWorkflow / Studio / Image history / skill handlers / model runtime. ثم إغلاق فجوة واحدة end-to-end: إزالة الخلفية + mask QA + تعديل يدوي + حفظ مشتق + مقارنة + تنزيل + tests + قياس.
